# Superpowers — ldt116 Fork

Fork of obra/superpowers, fine-tuned to change how coding-agent harnesses behave. Install from this repository, not the official marketplaces (see README).

## Tuned Divergences from Upstream

Every intentional difference from upstream is listed here. When merging upstream updates, preserve these.

1. **Planning and execution are phase-split; subagent-driven development remains the default execution mode.** After saving a plan, `writing-plans` hands execution to a fresh session — never the authoring one, whose context carries the brainstorm, the spec, and every plan draft — with a pointer-only prompt (issue ref or plan path, worktree/branch, REQUIRED SUB-SKILL: superpowers:subagent-driven-development); the implementing session fetches the plan itself. It still never offers an execution choice. One clean-context implementation subagent is the fallback when fresh sessions aren't available; `superpowers:executing-plans` is the fallback for harnesses without subagent access only.
2. **Independent review during inline plan execution.** `executing-plans` runs an independent review after every task — a dispatched reviewer subagent, or a fresh-eyes self-review when subagents are unavailable — plus one final whole-plan review before finishing.
3. **Fork packaging identity.** The marketplace is `superpowers-ldt116` (both manifests; asserted by `tests/codex/test-marketplace-manifest.sh`). Marketplace `owner` is ldt116 and `.claude-plugin/plugin.json` `repository` points at the fork; `author` credits stay with upstream (Jesse Vincent).
4. **Hardened review contract.** Review seats trust code over claims: risk diffs (write paths, auth/secrets/permissions, concurrency, plan-named risks) are re-verified by the reviewer at the review head; other diffs need command-and-output evidence, and prose verdicts are findings. Reviews never approve without requirements ("No — requirements not reviewed"). Implementer reports end with an evidence-based Self-review line, audited by the task reviewer. Deferred debt outlives the workspace (follow-up issue or in-repo debt register). Mutation-verify and cross-family reviewers where runnable.
5. **Gate artifacts live on the issue that tracks the work; internal artifacts are never tracked.** Plans (`writing-plans`) and specs (`brainstorming`) — the documents a human reviews and approves — go on the repository's tracker (GitHub, Gitea, …) when it has one: posted as a comment on the existing issue for that work, or a new `Plan:`/`Spec:` issue only when none exists — one work item keeps one issue, never a second. The `docs/superpowers/` file paths are the no-tracker fallback, and specs are no longer auto-committed to git. Workspace-internal artifacts (task briefs, implementer reports, review packages, ledgers) exist only to be run — nobody reads them after — so they stay in git-ignored scratch and are never posted. When a plan lives on an issue, `subagent-driven-development` materializes it into git-ignored scratch (`.superpowers/plans/`), and on a clean final review posts the final summary — composed in the workspace, posted by path — to that issue and closes it (unless it tracks work beyond the plan) before deleting the workspace.
6. **Main-chat leanness is a session rule.** `using-superpowers` — injected at every session start — carries a "Keep the Main Chat Lean" contract: the main conversation holds decisions, dispatches, rulings, and conclusions; file contents, command output, and diffs reach it only as targeted extracts (grep hits, ranged reads, redirected-output excerpts) or subagent digests — never bulk payloads. Micro-tested when added: 5v5 reps, control median 133KB ingested into context vs treatment 6.5KB, distributions fully separated with correctness intact. `subagent-driven-development` enforces the same rule at its boundaries: hand-composed dispatches carry the return contract (under 15 lines back, detail in the report file), and tracker-bound bodies — issue comments, PR bodies, the final summary — are composed as files and posted by path, never inline through string-only tracker tools.

When this list changes, update the fork section of README.md to match. The README lists behavioral divergences only — packaging identity (#3) stays out of it; the manifests and the test carry it.
